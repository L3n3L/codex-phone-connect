# Codex 手机电脑桥接对接复盘

更新时间：2026-10-06

## 1. 目标

手机浏览器输入文字或上下滑动，电脑本地程序把操作提交到用户当前绑定的 Codex 桌面窗口。

第一阶段只做：

- 原生 WPF 校准窗口；
- 局域网 HTTP 接收入口；
- 扫码进入的最小手机输入页；
- 输入框、发送按钮和聊天区域的相对坐标保存；
- 校准时绑定当前 Codex 窗口，运行时校验窗口仍然有效；
- 手机滑动达到阈值后，在拖动过程中持续发送滚动增量；
- 发送和滚动共用串行输入队列。

第一阶段不做：

- Thread 列表、Thread ID 识别和历史渲染；
- Codex 回复同步；
- 手机端聊天画面或截图同步；
- 云服务和账号系统；
- 通过 UI Automation 读取 Codex 内部 Web 控件。

## 2. 已验证事实

### 2.1 Windows UI Automation

对当前 ChatGPT/Codex 桌面进程进行只读 UIA 检查后，窗口树能看到 Chromium 外壳和 `RootWebArea`，但没有可用的聊天 `Edit` 控件和发送 `Button` 控件。因此不能把 UIA 的控件属性作为主链路。

### 2.2 Codex app-server

独立 app-server 进程可以完成初始化、Thread 列表和已知 Thread 的读取；已知 Thread 的历史可以由外部页面渲染。但这不等于可以读取桌面端当前选中的 Thread，也不能默认加入桌面端当前 writer。

一次对当前活跃 Thread 的外部写入尝试返回 `already has an active writer`，说明桌面端正在写入时存在并发写入限制。因此第一阶段不把 app-server 写入和桌面 UI 注入混在一起。

### 2.3 本机环境

- Windows 11
- .NET SDK 8.0.408
- WPF runtime 已安装
- 适合使用 C# / .NET 8 / WPF 做桌面端

## 3. 稳定的第一阶段架构

```text
手机浏览器
    │ POST /api/jobs /api/control/scroll
    ▼
Bridge.exe（WPF）
    ├─ 校准 UI
    ├─ 局域网 HTTP 服务
    ├─ 单线程任务队列
    └─ Windows 输入适配器边界
           │
           ▼
      Codex 当前绑定窗口
```

## 4. HTTP 契约

### `GET /api/status`

返回 Bridge 是否运行，以及手机应使用的访问地址。

### `GET /`

返回最小手机输入页。二维码编码的就是这个地址，手机和电脑在同一 Wi-Fi 时可以直接打开。

### `POST /api/jobs`

请求：

```json
{
  "text": "要发送给 Codex 的内容",
  "requestId": "手机端生成的唯一 ID",
  "token": "局域网配对码"
}
```

第一阶段返回：

```json
{
  "jobId": "服务器生成的任务 ID",
  "status": "queued"
}
```

### `POST /api/control/scroll`

手机端在滑动超过 36px 阈值后，持续发送相邻触摸位置的滚动增量：

```json
{
  "deltaY": -8,
  "requestId": "gesture-id-17",
  "token": "局域网配对码"
}
```

`deltaY` 为手机相邻触摸位置的像素差。负数表示手机上滑，Bridge 转换为反向 Windows 鼠标滚轮，使内容向下；正数表示手机下滑，使内容向上。手机端保持单飞请求，网络返回前产生的新增量会合并到下一次请求，避免请求堆积。

## 5. 校准数据

保存相对于 Codex 客户区的比例，不保存绝对屏幕坐标：

```json
{
  "inputPoint": { "x": 0.50, "y": 0.92 },
  "sendPoint": { "x": 0.94, "y": 0.92 },
  "scrollPoint": { "x": 0.55, "y": 0.45 }
}
```

这样可以适应窗口移动和大小变化；DPI 或布局变化后允许重新设置。

## 6. 会话边界

Bridge 的目标是“输入注入到校准时绑定的 Codex 窗口”。它不承诺识别 A/B Thread：

```text
Codex 当前选中 A → 手机发送 → A
Codex 切换到 B   → 手机发送 → B
```

如果用户在任务排队期间切换会话，Bridge 无法从 UIA 确认 Thread 身份；如果用户在 Codex 内切换会话，输入和滚动仍作用于同一个 Codex 窗口的当前界面。任务必须串行，并在目标窗口无效或不是 Codex 时拒绝输入。

窗口选择优先级：校准时捕获的有效窗口句柄 → 当前前台且进程名为 `ChatGPT` 的窗口 → 第一个可见的 `ChatGPT` 主窗口。绑定窗口失效且无法重新发现时，Bridge 记录失败日志，不把输入发送到其他应用。

## 7. 风险和处理

| 风险 | 处理 |
| --- | --- |
| Codex 没有在前台 | 拒绝发送，不发送到其他应用 |
| 窗口位置变化 | 使用客户区比例坐标 |
| DPI/显示器变化 | 允许重新设置坐标 |
| 多条消息并发 | 单线程队列和发送锁 |
| 剪贴板恢复过早 | 粘贴后等待，并仅在剪贴板仍是本次内容时恢复 |
| 局域网不可访问 | 显示实际地址，并提示 Windows 专用网络防火墙 |
| 多网卡选错地址 | 优先选择有默认网关的物理网卡，避免使用 VMware/TAP 等虚拟网卡 |
| 锁屏或权限级别不同 | 标记失败，不伪称已发送 |

## 10. 手机遥控滚动复盘

### 10.1 为什么不先做聊天记录迁移

当前目标是让用户在手机上控制电脑上的 Codex，而不是把 Codex 重新实现成手机聊天客户端。手机不显示聊天内容，可以避开 Thread 识别、历史数据库内部格式、Markdown/工具输出重渲染和回复同步竞态。

### 10.2 新的核心链路

```text
手机 pointermove
    │ 每帧累积增量，保持单飞 HTTP 请求
    ▼
POST /api/control/scroll
    ▼
Bridge 单线程输入队列
    ▼
校验绑定窗口 → 激活 Codex → 定位聊天区域 → 注入 Windows 滚轮
    ▼
电脑 Codex 当前窗口实时滚动
```

手机仍然通过 `/api/jobs` 发送文字；发送和滚动共用同一条队列，避免鼠标事件和键盘/剪贴板事件同时发生。

### 10.3 当前实现边界

- 手机只发送相邻触摸位置的 `deltaY`、请求 ID 和配对信息，不接收聊天正文；
- Bridge 不读取 Thread、不读取聊天数据库、不截取桌面；
- 滚动目标是校准时绑定且运行时仍有效的 Codex 窗口和聊天区域；
- 手机上滑映射为电脑内容向下滚动，手机下滑映射为电脑内容向上滚动；
- 如果 Codex 未启动、不可见或无法激活，Bridge 拒绝操作并记录日志。

### 10.4 新增配置

```json
{
  "inputPoint": { "x": 0.50, "y": 0.92 },
  "sendPoint": { "x": 0.94, "y": 0.92 },
  "scrollPoint": { "x": 0.55, "y": 0.45 }
}
```

`scrollPoint` 是 Codex 主聊天内容区域内的一个点。滚动时只把鼠标移动到该点，不点击。

### 10.5 验收标准

1. 手机上滑时，电脑 Codex 聊天区域向下滚动。
2. 手机下滑时，电脑 Codex 聊天区域向上滚动。
3. 短距离触摸不触发滚动。
4. 发送消息和滚动不会并发注入输入事件。
5. 手机页面不显示聊天正文或截图。
